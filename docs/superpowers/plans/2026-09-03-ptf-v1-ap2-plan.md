# PTF v1 AP2 Integration Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Prove PTF continuing delegation and exact transaction narrowing against the current AP2 Python SDK using real SD-JWT/KB-SD-JWT mandate chains, protected holder signing, selective disclosure, authenticated merchant binding, and receipt reconciliation without turning AP2 mandates into canonical PTF authority.

**Architecture:** `adapters/ap2` is a concrete AP2 integration around `MandateClient`, current Open/Closed Payment/Checkout Mandates, and `ReceiptClient`. PTF resolves authority and selects an ExecutionPlan first; AP2 artifacts are then minted/presented as protocol-specific Evidence Artifacts. A separate AP2 signing executor holds issuer/holder keys. The final task compares the completed x402 and AP2 implementations and extracts a shared protocol seam only if both genuinely need one; “no common adapter interface yet” is an acceptable and preferred outcome over speculative generalization.

**Tech Stack:** Python 3.14.7; uv; AP2 source pinned to Git commit `e1ea56db72a6385bce3e5c1112b3a56ce60acb43`; AP2 declared dependencies `cryptography==46.0.5`, `jwcrypto==1.5.6`, `pydantic==2.12.5`, `sd-jwt==0.10.4`; existing PTF runtime/PostgreSQL stack; pytest; Ruff; Pyright.

**Spec:** `docs/spec/PTF-V1-PROPOSED.md`, exact approved blob recorded by `docs/spec/PTF-V1-APPROVAL.md`. Primary sections: 8–17, 19, 22, 28.

## Global Constraints

- Execute only after Plan 01. The AP2/x402 seam-review task executes only after both Plan 02 and the preceding Plan 03 tasks are accepted.
- Use the current AP2 SDK vocabulary and primitives: `OpenPaymentMandate`, `OpenCheckoutMandate`, `PaymentMandate`, `CheckoutMandate`, `MandateClient.create/present/verify`, and `ReceiptClient`.
- Do not implement against obsolete simplified AP2 examples or invent replacement mandate schemas.
- PTF Standing Grant / Exact Human Approval remains canonical authority; AP2 mandate chains are protocol Evidence Artifacts generated only after PTF authorization requirements are satisfied.
- An AP2 valid signature/chain MUST NOT cause a PTF deny/approval-required decision to become authorized.
- Open AP2 mandate issuance that represents continuing delegated authority requires an already deliberate, active PTF Standing Grant basis; it never creates the Standing Grant.
- Closed AP2 mandate content must be no broader than the selected PTF ExecutionPlan and source authority.
- AP2 `aud`, `nonce`, `cnf`, delegation chain, constraints, and disclosure hashing are protocol enforcement/evidence and must be mapped truthfully in the PTF Enforcement Map.
- AP2 holder/issuer private keys never appear on Agent/API/receipt/log surfaces.
- `hash_mode="issuer_jwt_hash"` may be used only when the selected PTF plan explicitly permits downstream disclosure minimization; otherwise use `sd_hash` to lock exact forwarded disclosures.
- Receipt references remain AP2-specific evidence references, not Execution Grant IDs.
- Do not introduce a generic protocol adapter interface before the final cross-adapter review.
- Every task follows red-green-refactor and ends with a reviewable commit.

## Plan 03 completion gate

Plan 03 is accepted only when:

1. the exact AP2 source commit and declared dependencies are verified;
2. the converged dependency set passes every previously completed test before AP2 code is added;
3. continuing AP2 authority artifacts require an existing deliberate PTF Standing Grant;
4. closed mandates are no broader than selected PTF ExecutionPlan/source authority;
5. AP2 chain `cnf`, `aud`, `nonce`, constraint, and disclosure semantics are verified using upstream SDK primitives;
6. private holder/issuer key material remains outside Agent surfaces;
7. selective disclosure cannot exceed the PTF DisclosurePlan;
