# PTF v1 x402 Integration Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Prove PTF payment authority against x402 v2 by translating authenticated payment requirements into PTF Action Requests, reserving authority through the durable runtime, producing payment artifacts through a protected wallet executor, and reconciling settlement without exposing reusable wallet authority to the Agent.

**Architecture:** `adapters/x402` is a concrete x402 integration, not an implementation of a speculative universal adapter interface. It interprets x402 requirements, constructs x402-specific Enforcement Map evidence, and coordinates the already-established `ActionRuntime`. Wallet signing lives in a separate protected executor whose signer/key is never returned to the Agent or control-plane DTOs. x402 SDK policy/spend controls are defense-in-depth only; canonical authority remains PTF Hard Policy + Standing Grant / Exact Human Approval.

**Tech Stack:** Python 3.14.7; uv; `x402==2.22.0`; x402 EVM exact mechanism for the reference fixture; Pydantic 2.x; pytest; Hypothesis; existing PTF runtime/PostgreSQL stack. Pin the x402 2.22.0 wheel/source through `uv.lock`; verify PyPI wheel SHA-256 `e2908fe1493144bfb2b7e624d0373eed70ce2af1b445f55e2c91e6502140bce2` and source provenance commit `23c7a9751ae4033de60cf6e9111a931869eecbe7` before execution.

**Spec:** `docs/spec/PTF-V1-PROPOSED.md`, exact approved blob recorded by `docs/spec/PTF-V1-APPROVAL.md`. Primary sections: 13–17, 19, 22, 28.

## Global Constraints

- Execute only after Plan 01 completion and independent acceptance of the `ActionRuntime` public seam.
- Use x402 v2 semantics for this proof; do not add compatibility code for x402 v1 unless a concrete required integration appears later.
- x402 `PaymentRequired` / `PaymentRequirements` are protocol inputs, not PTF authority objects.
- PTF `ActionRequest`, `ExecutionPlan`, `EnforcementMap`, `ExecutionGrantRecord`, `ExternalExecutionResult`, and `PTFReceipt` remain canonical.
- x402 client `spend_controls`, policies, selector behavior, facilitator verification, or settlement success MUST NOT create or broaden PTF authority.
- Payment payee identity, payment address, HTTP/resource origin, facilitator endpoint, asset, and network remain distinct until represented by validated PTF bindings.
- The wallet signer/private key is held only inside the x402 protected-executor process/object for the reference profile and is never returned by API/Agent DTOs.
- `ProtectedResourceRef` alone is insufficient to call the wallet executor; a current Execution Grant + selected plan + recipient/payment binding are required.
- A timeout/transport failure after a payment artifact may have been submitted is `INDETERMINATE` unless independent evidence proves no effect or exact idempotent retry safety.
- No generic `ProtocolAdapter`, `PaymentAdapter`, or adapter registry is introduced by this plan.
- All x402-specific protocol artifacts remain Evidence Artifacts referenced by digest/ID from PTF receipts.
- Every task uses failing tests first, minimal implementation, passing tests, refactor, then commit.

## Plan 02 completion gate

Plan 02 is accepted only when:

1. x402 2.22.0 provenance/hash is locked;
2. payment requirements translate to PTF ActionRequest without becoming authority;
3. payee/payment endpoint/network/asset/amount are bound and enforced truthfully;
4. CP2 reservation happens before usable payment authority;
5. wallet signing occurs behind a protected executor and reusable key material is absent from Agent surfaces;
6. facilitator/x402 validation is treated as protocol evidence/defense-in-depth, not PTF authority;
7. successful settlement consumes, proven no-effect releases, ambiguous post-submit failure holds `INDETERMINATE`;
8. recipient/amount/replay substitution attacks fail;
9. x402 protocol artifacts remain separate from PTF authority records;
10. no universal protocol-adapter abstraction exists.

After acceptance, retain the concrete x402 implementation unchanged until Plan 03 AP2 is also accepted and the explicit cross-adapter seam review is performed.
