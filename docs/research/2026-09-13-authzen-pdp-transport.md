## 1. Authorization API 1.0 Final — status and shape

- Status is **Final**, published 11 January 2026, authors Gazitt (Aserto) / Brossard (Axiomatics) / Tulshibagwale (SGNL). The specs page lists it as the single Final specification, approved January 2026. (https://openid.net/specs/authorization-api-1_0.html) (https://openid.net/wg/authzen/specifications/)
- The API is served by the PDP and called by the PEP; it covers evaluation endpoints (single + batch decisions) and search endpoints (discover permissible subjects/resources/actions). Policy language, architecture, and state management are explicitly out of scope. (https://openid.net/specs/authorization-api-1_0.html)
- **Transport-agnostic model, normative HTTPS binding.** §2: "The Authorization API is defined in a transport-agnostic manner. A normative HTTPS binding is described in Transport (§10). Other bindings, such as gRPC, may be defined in other profiles." §10: the HTTPS+JSON binding "MUST be implemented by a compliant PDP"; future gRPC/CoAP bindings MAY be defined as profiles. (https://openid.net/specs/authorization-api-1_0.html)
- **Versioning (§4):** this document is API version 1.0; later revisions MAY augment but MUST NOT modify the API described here. Endpoints for v1 SHOULD include `v1` in the endpoint identifier (e.g. `https://pdp.example.com/access/v1/`). (https://openid.net/specs/authorization-api-1_0.html)

## 2. Evaluation endpoints — method, paths, envelopes

- All API requests in the HTTPS binding are HTTPS `POST` with `Content-Type: application/json`; top-level body MUST be a JSON object; success is `200` + `application/json`. Receivers MUST ignore unknown fields and MUST NOT assume member ordering. (https://openid.net/specs/authorization-api-1_0.html)
- Endpoint table (§10.1, Table 1) — exact default paths and metadata parameters: (https://openid.net/specs/authorization-api-1_0.html)
  - Access Evaluation: `POST /access/v1/evaluation` (`access_evaluation_endpoint`), request §6.1 → response §6.2.
  - Access Evaluations (batch/boxcar): `POST /access/v1/evaluations` (`access_evaluations_endpoint`), request §7.1 → response §7.2.
  - Subject / Resource / Action Search: `POST /access/v1/search/subject|resource|action` (`search_subject_endpoint` etc.), requests §8.4.1/8.5.1/8.6.1 → common response §8.3.
- Request envelope (single): `{subject*, action*, resource*, context?}` where subject/resource are `{type*, id*, properties?}`, action is `{name*, properties?}`, context is a free-form object. (https://openid.net/specs/authorization-api-1_0.html)
- Batch envelope: top-level `subject/action/resource/context` act as **defaults** for an `evaluations[]` array of per-evaluation objects; per-entry values override defaults; any of the three required keys omitted per-entry MUST be present top-level. Absent/empty `evaluations[]` behaves as a single evaluation (backwards compatible). `options.evaluations_semantic` selects `execute_all` (default) / `deny_on_first_deny` (&&) / `permit_on_first_permit` (||). (https://openid.net/specs/authorization-api-1_0.html)
- Response envelope: `{decision*: boolean, context?}`; `true` = permit (PEP MAY still reject if it does not understand `context`), `false` = MUST NOT permit. Batch response mirrors with `evaluations[]` of Decisions in request order; top-level `decision` SHOULD be omitted when `evaluations[]` is present. `context` semantics are implementation-defined (reasons, advice/obligations, step-up hints such as `acr_values`/`amr_values` in non-normative examples). (https://openid.net/specs/authorization-api-1_0.html)
- Search: PEP omits the `id` of the entity being queried; response is `{page?, context?, results*[]}` with pagination via opaque `page.token` / `next_token` (empty string = end). Results SHOULD evaluate to `decision:true` if re-checked, but this is not guaranteed. (https://openid.net/specs/authorization-api-1_0.html)

## 3. Error semantics — transport errors vs deny

- Deny is **not** an error: "A successful request that results in a 'deny' is indicated by a 200 OK status code with a `{ "decision": false }` payload." HTTP errors "are unrelated to the outcome of an authorization decision and are distinct from it." (https://openid.net/specs/authorization-api-1_0.html)
- Transport-level error codes (§10.1.2, Table 2), body is an error message string: `400` Bad Request (also used when a required information-model attribute is omitted, §10.1.1), `401` Unauthorized, `403` Forbidden, `500` Internal Error. (https://openid.net/specs/authorization-api-1_0.html)
- `401` specifically means the **PEP failed to authenticate to the PDP** (missing/invalid `Authorization` header or token) — not that the subject was denied. (https://openid.net/specs/authorization-api-1_0.html)
- Batch split (§7.2.1): whole-payload failures go to the transport layer (4XX/5XX); per-evaluation failures stay in-band as `"decision": false` with the failure described in `context` (e.g. `context.error: {status: 404, message: "Resource not found"}`); decisions default closed. (https://openid.net/specs/authorization-api-1_0.html)

## 4. PEP↔PDP authentication and transport security

- Authentication for the API itself is **out of scope**; "Support for OAuth 2.0 is RECOMMENDED" (§2). The worked HTTPS examples use `Authorization: Bearer <token>`. (https://openid.net/specs/authorization-api-1_0.html)
- Confidentiality/integrity (§11.1): the PEP–PDP connection "is the most sensitive one"; it MUST be secured "using the most adequate means given the choice of transport (e.g. TLS for HTTP REST)." (https://openid.net/specs/authorization-api-1_0.html)
- PEP authentication (§11.2): the PDP **SHOULD** authenticate the calling PEP (mitigates policy-probing/DoS); mechanisms are out of scope but MAY include **mutual TLS, OAuth-based authentication, or API key**. Strength/choice not specified. (https://openid.net/specs/authorization-api-1_0.html)
- Auth failure (§11.3): missing/invalid credentials → PDP MUST respond `401` and SHOULD include `WWW-Authenticate` (framework per RFC 2617), e.g. `WWW-Authenticate: Bearer realm="https://as.example.com"`. (https://openid.net/specs/authorization-api-1_0.html)
- Trust model (§11.4): the PDP **must trust the PEP** — PEP-supplied subject/resource/action/context attributes are taken at face value; the PEP is ultimately responsible for enforcing the decision. (No attribute-integrity mechanism in the base spec.) (https://openid.net/specs/authorization-api-1_0.html)
- Response integrity is optional (§11.6): the PDP MAY sign authorization responses (non-repudiation past intermediaries where TLS terminates); no mandatory signature scheme. JSON payloads SHOULD follow the I-JSON profile (UTF-8, IEEE-754-safe numbers, unique member names); null-valued properties SHOULD be omitted to avoid absent-vs-null ambiguity. PDPs SHOULD rate-limit / bound payload sizes (§11.7). (https://openid.net/specs/authorization-api-1_0.html)
- Request IDs (§10.1.3): PEP MAY send `X-Request-ID` (arbitrary string); if present the PDP MUST echo the same value back (RECOMMENDED via response `X-Request-ID`). Correlation only — not auth. (https://openid.net/specs/authorization-api-1_0.html)
- Discovery (§9): PDPs SHOULD publish metadata at `/.well-known/authzen-configuration` (RFC 8615, IANA-registered suffix). `policy_decision_point` (https URL, no query/fragment) is REQUIRED, `access_evaluation_endpoint` REQUIRED, evaluations + three search endpoints OPTIONAL — absence of an endpoint parameter tells the PEP that API is unsupported. Optional `capabilities[]` (IANA URNs) and `signed_metadata` (JWS/JWT with `iss`; takes precedence over plain JSON when the PEP supports it). `policy_decision_point` MUST match the URL the metadata was fetched from (mix-up defense); normal HTTP caching applies. (https://openid.net/specs/authorization-api-1_0.html)

## 6. Reference PDP implementations

- **openid/authzen repo is spec + interop harness, not a PDP.** Contents: `api/` (spec markdown, built to HTML via kramdown/xml2rfc), `profiles/`, `certification/`, `interop/` (Todo-app scenario, results at authzen-interop.net). No standalone reference PDP server ships in the repo. (https://github.com/openid/authzen)
- **Interop PEP surface (TypeScript Todo backend)** shows the de-facto wire expectation: authorization middleware POSTs to `${AUTHZEN_PDP_URL}/access/v1/evaluation` (and `/access/v1/evaluations` for the -02 suite), with an `Authorization` header carrying a per-PDP `Basic`/`Bearer` API key from `AUTHZEN_PDP_API_KEY`; runnable conformance suites per spec version (`authorization-api-1_0-00/01/02`). I.e. in practice: bearer/basic API key over TLS, metadata-or-convention endpoint URLs. (https://raw.githubusercontent.com/openid/authzen/main/interop/authzen-todo-backend/README.md)
- **Topaz (aserto-dev/topaz): Go service, OPA as decision engine, Zanzibar-inspired embedded directory.** REST authorizer at `POST https://localhost:8383/api/v2/authz/is` with its own envelope (`identity_context` + `policy_context.path/decisions`), plus gRPC (`localhost:8282`) and directory (`localhost:9292`) endpoints; ships self-signed certs (`certs/`); policy distributed as signed OCI images. Its wire format is Topaz-native, **not** AuthZEN SARC — Topaz participates in the AuthZEN interop as a PDP behind an AuthZEN façade, but conformance of any given release is UNVERIFIED here (see gaps). (https://github.com/aserto-dev/topaz)
- **OPA (open-policy-agent/opa): Go (repo carries `.go-version`, `go.mod`, CNCF-graduated).** Decision surface is the Data API: `POST /v1/data/{path}` with `{"input": ...}` → `{"result": ..., "decision_id"?}`; undefined paths return 200 _without_ `result` (contrast AuthZEN's explicit `decision:false`). PEP authentication is deployment-configured and **off by default**: `--authentication=token` (Bearer → `input.identity`) or `--authentication=tls` (mTLS client certs, verified against `--tls-ca-cert-file`), paired with `--authorization=basic` and a `system.authz` Rego policy; TLS via `--tls-cert-file/--tls-private-key-file`; default bind is localhost; unauthenticated-denied requests return `401 {"code":"unauthorized"}`. Like Topaz, OPA's native API is not AuthZEN SARC — an AuthZEN PDP can be _built on_ OPA, but OPA out of the box is not one. (https://github.com/open-policy-agent/opa) (https://www.openpolicyagent.org/docs/latest/rest-api/) (https://www.openpolicyagent.org/docs/latest/security/)

## 7. Obligations profile — what a PDP must implement beyond allow/deny

- Draft 1 (Babeanu/Indykite, July 2026). Design: obligations ride **exclusively inside the existing open-ended `context` member** (`context.obligations[]`), so PDPs that ignore the profile just never emit the key and old PEPs are unaffected. **No new endpoint** — the endpoint surface is unchanged; only decision-response content and metadata gain members. (https://openid.github.io/authzen/authzen-obligations-profile-1_0.html)
- Obligation object: `{id* (unique within response), type* (IANA-registered or `custom`), properties*}`. Order is non-normative; all listed obligations are mandatory and independent. (https://openid.github.io/authzen/authzen-obligations-profile-1_0.html)
- Normative types: `step-up` (`acr_value*`, `amr_values?`), `notification` (`to*`, `body*`, `topic?`; transport-agnostic destination), `session_termination` (`subject*`), `filter` (`filter*` — opaque JSON, bilaterally-agreed syntax; e.g. RAR-style `authorization_details` caps), `custom` (bilateral semantics). Registry: IANA "AuthZEN Obligation Types", Specification Required. (https://openid.github.io/authzen/authzen-obligations-profile-1_0.html)
- PEP compliance (the load-bearing rule): on PERMIT, access is _conditioned_ on executing every obligation — non-compliance flips the response to DENY. On DENY, access stays denied and obligations are additive (logging/notify). Unknown/unimplemented/malformed/failed obligation = "cannot comply" → DENY (except Search, where only the non-compliant _result_ is excluded). A PEP MUST still execute the obligations it does understand even while downgrading to DENY. `filter` + DENY on non-search requests is a MUST-NOT-issue combination. (https://openid.github.io/authzen/authzen-obligations-profile-1_0.html)
- Discovery/negotiation: PDP advertises `supported_obligations[]` in its metadata document (MUST include if it implements the profile; absence = none); PEP MAY declare `context.supported_obligations[]` per request, restricted to values the PDP advertised. Negotiation is **advisory** — the PDP may still issue an undeclared type and the PEP must fail closed per above. No attestation of execution exists in-protocol; PDPs relying on obligations for critical controls SHOULD verify PEP compliance out of band; `notification.to/body` MUST be treated as untrusted input by PEPs. (https://openid.github.io/authzen/authzen-obligations-profile-1_0.html)

## 8. Access Request and Approval profile — endpoint-surface impact (for completeness)

- Draft 1 (McGuinness, 10 Sept 2026). Preserves allow/deny: "a denied decision remains a denial and MUST NOT be treated as access." Adds: requestable-denial context, an access-request endpoint, an opaque task handle, and re-evaluation so the PDP stays authoritative at enforcement time. Stateless PDP: durable request/approval state lives in the Access Request Service role (which MAY be the PDP itself, a trusted governance service, or an independent service). (https://openid.github.io/authzen/authzen-access-request-approval-profile-1_0.html)
- Endpoint-surface delta (the only profile here that adds endpoints): discovery via PDP metadata `access_request_endpoint` (MUST be HTTPS URI) + capability URN `urn:openid:authzen:capability:access-request` (+ `jwks_uri` when signed artifacts are used). Submission `POST /access/v1/requests` (examples; actual URL is the advertised metadata value, overridable per-denial by `access_request.endpoint`); task handle is a `status_endpoint` URL (`/access/v1/requests/{id}`) plus a `cancel` link; task states `pending/.../cancelled/partial` with error URNs under `urn:openid:authzen:access-request:error:*`. Denial binding is by value (`binding_token`, integrity-protected, SHOULD be JWS — REQUIRED form for independent services) or by reference (`evaluation_id` + `evaluated_at` in decision context, shared-state deployments only). (https://openid.github.io/authzen/authzen-access-request-approval-profile-1_0.html)

## 9. COAZ-MCP — transport verdict: TRANSPORT-AGNOSTIC (no new PDP transport)

- COAZ Framework (Draft 1, Feb 2026, Olivier/Cerbos + Tulshibagwale) is a **protocol-neutral mapping layer**, not a transport: it projects an arbitrary protocol's inputs through a declarative mapping (literals + CEL expressions, default `$` discriminator / `$$` escape) into a standard AuthZEN Access Evaluation(s) request selected by the mapping's envelope (`evaluation` | `evaluations`). It defines **no mapping for any specific protocol** and **no wire security of its own** — "All communication between the PEP and the PDP MUST use TLS, as specified in the transport requirements of [AUTHZEN]" (§5.4). Error reporting _to the caller_ is explicitly binding-defined ("the transport used to report each category to the caller is binding-defined, because it depends on the protocol"). (https://openid.github.io/authzen/authzen-coaz-framework-1_0.html)
- COAZ-MCP (Draft 1, Feb 2026) binds the framework to MCP: input variables are `params` (the JSON-RPC params) and `token` (decoded JWT OAuth access-token claims); fixed default mappings per MCP method (e.g. `tools/call` → `action: tools/call`, `resource: {type: tool, id: $params.name}`, `subject: {type: identity, id: $token.sub}`, `context.agent: $token.?client_id`); servers MAY override per-tool via `x-authzen-mapping` in the tool `inputSchema` (discoverable through `tools/list`); `ping` and `notifications/*` are explicit pass-throughs; unknown methods fail closed. (https://openid.github.io/authzen/authzen-coaz-mcp-binding-1_0.html)
- MCP-side error transport is JSON-RPC-shaped, PDP-side is unchanged AuthZEN: mapping error → `-32602`, denial → `-32001` (implementation-defined range; `-32401`-style codes explicitly non-conformant), PDP communication failure → `-32603`. PEP behavior requires token validation (sig/iss/aud/exp, RFC 8707 audience binding), trust-anchored `subject.id` verified against the token claim (override allowed only with a SHOULD-warn), and an operation-binding check (no transplanting a permit onto a changed message). **Verdict: COAZ-MCP implies no transport of its own** — the PEP↔PDP leg reuses the base Authorization API binding (HTTPS POST + TLS), and only the PEP↔caller leg speaks the bound protocol's error framing. (https://openid.github.io/authzen/authzen-coaz-mcp-binding-1_0.html)

## Key takeaways

- A minimal conformant PDP is an **HTTPS JSON POST endpoint**, not a new protocol: checklist in §10 below. AuthZEN standardizes the SARC envelope and decision/error contract; it deliberately does **not** standardize PEP credential type — any of mTLS / OAuth bearer / API key satisfies the SHOULD, and the interop field reality is bearer-or-basic API keys over TLS.
- Obligations change **response content + metadata**, not endpoints; Access-Request-and-Approval is the only profile that adds endpoints (`/access/v1/requests` family). COAZ-MCP changes **neither** — it is a mapping plus caller-side error framing.
- For PTF purposes (offline, citation-carrying allows): AuthZEN's online round-trip per decision plus its trust-the-PEP input model remain the disqualifiers from the 09-09 note; nothing in the Final or the drafts changes that. Reusable pieces are the SARC envelope shape, the deny-vs-error split (deny = 200 + `decision:false`), and the fail-closed obligation semantics.

## Minimal conformant PDP endpoint checklist

1. `POST` JSON at the advertised `access_evaluation_endpoint` (default path `/access/v1/evaluation`); accept `{subject*, action*, resource*, context?}`; ignore unknown fields. (https://openid.net/specs/authorization-api-1_0.html)
2. Always answer successful evaluations with `200` + `{decision: boolean, context?}` — including denials (`decision:false`). Reserve `400/401/403/500` (string body) for transport/payload/auth failures. (https://openid.net/specs/authorization-api-1_0.html)
3. Serve `GET /.well-known/authzen-configuration` with `policy_decision_point` (+ matching identifier), `access_evaluation_endpoint`, and any optional endpoints/capabilities/`signed_metadata` supported. (https://openid.net/specs/authorization-api-1_0.html)
4. Terminate TLS; authenticate the PEP by at least one of mTLS / OAuth bearer / API key (SHOULD); emit `401` + `WWW-Authenticate` on PEP-auth failure; echo `X-Request-ID` when the PEP sends one. (https://openid.net/specs/authorization-api-1_0.html)
5. If batch is advertised, implement `evaluations[]` defaults/overrides and `options.evaluations_semantic` (`execute_all` default); keep per-item failures in-band as `decision:false` + `context`. (https://openid.net/specs/authorization-api-1_0.html)
6. If obligations are emitted: populate `context.obligations[]` with `{id, type, properties}`, advertise `supported_obligations[]` in metadata, register any new type in the IANA registry; never assume the PEP executed them. (https://openid.github.io/authzen/authzen-obligations-profile-1_0.html)
